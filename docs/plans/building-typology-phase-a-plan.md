# Planning-Theorem Artifact: Building Typology Phase A

## Executive Summary

- Goal: upgrade the OSM buildings visible in OpenAtlas from uniform warm-stone extrusions into a source-backed urban typology layer.
- Intent: make the first production step toward an ArcGIS Urban-quality civic planning surface: existing conditions, explainable building classes, confidence, zoning context, and future scenario readiness.
- Summary of work: adapt the downloaded Phase A typology spec to this repo family. The classifier and feature pipeline live in `civic-atlas-ingest`, tenant-safe storage and GraphQL live in `our-civic-atlas-backend`, and the public render channel lives in this repo's MapLibre/deck.gl path.

## Current Condition

- The public route is `MapLibre + deck.gl`, not the parked R3F branch. `AtlasMap.tsx` already renders OSM buildings through a deck.gl `GeoJsonLayer`.
- The current OSM fixture at `src/data/open-flint-atlas/fixtures/osm-buildings.json` contains 21,182 Flint building footprints generated by `scripts/fetch-osm-buildings.mjs`.
- OSM tags are sparse: most current footprints are `building=yes`, while only a small minority carry names, addresses, height, levels, or year tags. OSM-only visual coloring would therefore be a weak demo unless the UI clearly marks uncertainty.
- `LayerControls.tsx` has no dedicated OSM-building or typology toggle yet, even though the map layer is controlled internally by `layerVisibility.osmBuildings` / `layerVisibility.buildings`.
- `civic-atlas-ingest` already has Overpass, assessor, Ray, and training-corpus stubs, but no typology-specific schema, feature snapshot, classifier, calibration, or inference module.
- `our-civic-atlas-backend` already enables PostGIS and tenant-scoped RLS, so the downloaded SQL must be upgraded with `tenant_id` before it can be used here.

## Intent

The ambition is not merely "color buildings." ArcGIS Urban's current quality bar includes citywide 3D existing conditions, zoning and land-use scenario planning, metrics, project workflows, collaboration, and extendable planning systems. Phase A should therefore create a durable building intelligence substrate: each building has a class, confidence, class distribution, feature completeness, model version, and source history. The color channel is the visible first win, not the whole system.

## Goal

- User-visible outcome: OpenAtlas can show a `Typology` building layer with six classes: residential, commercial, industrial, civic, mixed use, and unknown.
- System behavior: building classification is deterministic for a given OSM snapshot, parcel/zoning snapshot, feature version, and model version.
- Data/model changes: `civic-atlas-ingest` gains typology schemas, feature extraction, labels, training, calibration, inference, and city-pack artifacts.
- Backend changes: PostGIS stores tenant-scoped building typology rows, and GraphQL exposes `typology { class confidence perClassProba featureCompleteness modelVersion }`.
- Frontend changes: deck.gl reads typology-bearing building features and maps them to semantic material colors, low-confidence styling, hover details, and a layer toggle.
- What must not regress: the current map remains the public base, no frontend secrets are added, low confidence is visible, and R3F stays parked except for selective Lost Flint overlays.

## Vision Delta

- Target vision: OpenAtlas can reason about existing buildings the way a planning tool does: use class, zoning context, parcel context, scenario metrics, and model confidence.
- Current visual condition: all current OSM buildings render with one material, so the city reads as mass but not as urban fabric.
- This plan makes true: a real typology pipeline, city pack, tenant-safe storage, GraphQL contract, and deck.gl render channel.
- This plan does not make true: full zoning scenario design, parcel development rules, building massing generation, or project e-submission. Those are later ArcGIS Urban-parity lanes.
- Visual downgrade risks: noisy colors, low-confidence buildings looking overconfident, mobile clutter, and replacing the familiar warm-stone layer before the typology layer earns it.
- Remaining gaps: stable zoning source verification, hand-labeled validation set, model calibration, low-zoom block aggregation, and scenario metrics.

## Test Strategy

- Preflight checks: verify current OSM feature count, zoning source URLs, PostGIS/RLS invariants, and package dependency lock impact.
- Focused tests: typology schema unit tests, feature extraction sample tests, calibration tests, inference idempotency test.
- Integration tests: Ray local smoke, backend migration/RLS smoke, GraphQL query smoke, frontend codegen.
- Regression tests: `npm run typecheck`, `npm run lint`, `npm run validate:atlas`, and route smoke for `/open-flint-atlas`.
- Manual smoke checks: desktop and mobile screenshots with warm-stone default, typology enabled, low-confidence examples, and zoom boundary.
- Performance/security checks: no service credentials in frontend, no personal parcel owner data in public fixtures, deck.gl frame budget under dense city view.
